# Public discovery and private clinical pages

The public landing page has Russian, Uzbek and English metadata and stable language URLs: `/`, `/?lang=uz`, `/?lang=en`. The server renders titles, descriptions, canonical and language links, Open Graph, Twitter cards, and a readable public fallback before JavaScript. The browser updates metadata on navigation. Patient names, record identifiers, query text and clinical results never enter titles, descriptions, social cards or structured data.

Public copy is provider-neutral. It does not advertise a fixed MedGemma model or local-only processing. Both the landing page and the server-rendered fallback disclose that selected clinical text/images go to the configured AI service and that cloud processing occurs at an external provider. The authenticated workspace shows the actual configured provider/model; synthetic prepared reviews remain separately labeled.

`/robots.txt` and `/sitemap.xml` are generated by the API server. Only the three public landing URLs can enter the sitemap. Private pages, sign-in, checkout, API responses and API documentation carry `X-Robots-Tag: noindex, nofollow, nosnippet, noarchive`; private HTML has matching meta tags and `Cache-Control: no-store`. Authentication and role checks protect the records. Robots rules alone are not access control.

There is no production domain yet. Local builds intentionally remain **not indexable** and do not invent canonical or social URLs. After a real HTTPS domain is configured, set these values in the server `.env` and restart it:

```dotenv
SITE_URL=https://YOUR-REAL-DOMAIN
SEO_INDEXING_ENABLED=true
```

`SITE_URL` must be an origin, without a path, query, fragment or credentials. Canonical, sitemap and social URLs use this value exclusively; a supplied Host or forwarded host header cannot alter them. Local/private IP and local/test domains remain non-indexable even when the flag is enabled. A staging deployment should keep `SEO_INDEXING_ENABLED=false`. Update `ALLOWED_ORIGINS` and HTTPS cookie settings for the deployment separately.

Deploy the built frontend through the Python application to obtain server metadata, public content fallback, robots and sitemap. A Vite-only static deployment needs equivalent routing and header rules; by default its HTML remains noindex. The fallback is a concise public product description, not a server-rendered copy of the full interactive page. The production domain owner can then verify their domain in Google Search Console and submit `/sitemap.xml`; those external account steps have not been performed.

Structured data describes the actual organization, website and web application. It includes no invented reviews, ratings, awards, clinical efficacy claims or static prices that could drift from the billing catalog. There is no guarantee of ranking, indexing or rich-result eligibility. The web manifest supplies browser icons only; no offline service worker is installed.

Reference: [Google developer SEO guidance](https://developers.google.com/search/docs/fundamentals/get-started-developers), [robots metadata](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag), [JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics).
